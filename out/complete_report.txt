WHAT DBT BUYS HERE, AND IT IS NOT SQL FOR ITS OWN SAKE:

  ONE definition of the calibration cutoff. It was retyped in the
  generator and again in the analysis; it is now a dbt var that every
  model referencing the boundary reads. A cutoff that lives in four
  files will eventually differ between two of them, and the resulting
  leakage is invisible in each query on its own.

  A LEAKAGE TEST THAT RUNS. `customer_holdout` is a separate model from
  `customer_rfm`, and a singular test FAILS THE BUILD if any holdout row
  falls on or before the cutoff. That was previously a convention, and
  a convention is a thing people follow until a deadline.

  A test that asserts a table is what it CLAIMS to be. `channel_daily`
  credits every channel that touched a converting journey, so its
  conversion column must sum to MORE than the true conversion count. A
  test asserts exactly that -- if it ever stops holding, someone has
  quietly turned a reach table into an attribution table, which is the
  most common analytics error in this domain.

  The orchestrator is 120 lines and not Airflow, on purpose. What a
  scheduler is FOR at this size is dependencies, idempotency and
  failure semantics -- a task whose upstream failed is marked skipped
  and never runs on stale inputs. Installing Airflow would demonstrate
  that Airflow installs.

  HONEST LIMIT: DuckDB. The models, the graph and the tests are real
  dbt and would run on Snowflake with a profile change. What is absent
  is everything about a warehouse that is hard -- concurrency, cost
  governance, permissions, incremental strategies at scale.

  stability (max ARI)                  k = 4
  forward separation (max adj eta^2)   k = 7

SIX CRITERIA, 3 DIFFERENT ANSWERS. That is the finding, and averaging
them would be the worst possible response to it.

  They disagree for principled reasons. Silhouette rewards compact
  spheres. Stability rewards coarse partitions -- k=2 is stable on
  almost any data because there is little to disagree about. Forward
  separation rewards whatever correlates with the outcome.

  The one that should decide is FORWARD SEPARATION, because it is the
  only criterion tied to what the segments are FOR. The rest measure
  whether the geometry is tidy, which is a question nobody in the
  business asked. And it is reported ADJUSTED, because raw eta^2 rises
  with k mechanically and an unadjusted table always recommends the
  largest k on offer.

HDBSCAN, which does not take k at all -- swept over min_cluster_size:

  min_cluster_size     clusters  noise share largest cluster
  25                          5       0.6197            923
  50                          2       0.3466           3101
  100                         0       1.0000              0
  200                         0       1.0000              0
  400                         0       1.0000              0

  Lowest noise share: 0.3466 at min_cluster_size=50.

  At its best setting HDBSCAN finds 2 clusters, and the largest holds
  63% of all customers; the rest is noise. That is one dense core, not
  a set of natural groups.

  THE COMPARISON IS NOT 'WHICH IS BETTER'. k-means forces a partition
  and is therefore always actionable and sometimes fictional -- it will
  cheerfully cut a single cloud into five wedges and name them. HDBSCAN
  refuses to invent structure and is therefore sometimes honest and
  often unusable. Which failure mode you prefer is a business decision,
  and the useful output of running both is knowing WHICH ONE you are
  buying: here the customers form one continuum, so the k-means
  segments are useful cuts through it, not groups that exist on their
  own. That is worth knowing before anyone builds a campaign on them.

  32x more permutations should cut Monte-Carlo error by 5.66x if the
  estimator were merely noisy. Measured: 2.23x.

IT DOES NOT CONVERGE, AND THAT IS THE RESULT OF RUNNING THE CHECK.

  The error falls a little and then plateaus around 0.051. More samples
  do not help, which means the gap is BIAS rather than variance -- the
  sampled estimator is converging to a different number than the exact
  one, not noisily to the same number.

  The cause is visible in the coalition count below: only 2126 of the 4096
  possible coalitions were ever observed. A permutation walks the
  lattice one channel at a time, and when the next coalition was never
  seen it cannot advance -- so permutations STALL, and they stall more
  often for channels that appear in rare combinations. The exact
  estimator has the same missing data but reweights by the coalitions it
  DID use; the sampler cannot, because it never learns which ones it
  skipped.

  So the two are not the same estimator at different sample sizes. They
  are different estimators, and the conclusion is that sampled Shapley
  on a SPARSE coalition lattice needs a different VALUE FUNCTION, not
  more permutations. Two of those are built and measured below.

  This is exactly the check the usual justification for sampling skips.
  'The exact version is intractable' is true at 30 channels and is also
  the regime where nobody can discover this. Twelve channels is the
  largest scale at which both answers exist, which is the only reason
  the discrepancy is visible at all.

C2. THE FIX -- TWO VALUE FUNCTIONS, AND THEY ARE NOT THE SAME FIX
==============================================================================
The previous section diagnosed the bias and left the repair as a note.
This is the repair, and it is measured against the same truth.

  The stall is now counted rather than inferred: the exact-set sampler
  stalls on 1978 of 4800 permutation steps (41.2%). A third of every walk
  lands on a coalition nobody was ever exposed to.

FIX 1 -- SUBSET-CLOSURE VALUE FUNCTION.
  v(S) = the conversion rate among journeys whose channel set is a
  SUBSET of S: 'what is achievable using only the channels in S'. The
  exact-set version asks 'what happened to people who saw exactly this
  combination and nothing else', which is a question about a rarer and
  rarer group as the coalition grows -- and is undefined once the group
  is empty.

  coalitions defined, exact-set : 2126 of 4096  (51.9%)
  coalitions defined, closure   : 4095 of 4096  (100.0%)

  The one undefined coalition is the empty set, which is correct: no
  channels is no marketing and that rate is zero by definition, not by
  missing data.

  Efficiency residual: -3.33e-16 against a grand-coalition value of 0.3225.
  The credits add up to the thing being attributed, to machine
  precision. That check is not available for the exact-set version at
  all, because its grand coalition is estimated from whichever handful
  of customers happened to see all twelve channels.

 n_perms  exact_set_err   closure_err
      25        0.07920       0.02445
      50        0.06855       0.01834
     100        0.06199       0.01160
     200        0.05059       0.00890
     400        0.04541       0.00626

  Both columns are averaged over 12 seeds, and that count had to be
  measured too. One seed read 8.10x and was non-monotone; six seeds
  read 6.44x. Both are ABOVE the 5.66x ceiling that 1/sqrt(n) sets --
  which is not a fast estimator but an unconverged measurement OF an
  estimator. It took twelve seeds to settle just under the ceiling,
  where it belongs. The same mistake, one level up.

     exact-set value function : 2.12x   (plateaus at 0.03744)
     closure value function   : 5.41x   (reaches 0.00452)

  IT CONVERGES. Same estimator, same permutations, same seed logic:
  the only thing that changed is the game being sampled. The stall
  count is 0 by construction, because there is no rung to fall off.

D. HIGHER-ORDER MARKOV -- WHAT A FIRST-ORDER CHAIN THROWS AWAY
==============================================================================
 order  n_states  thin_state_share  base_conversion  max_abs_removal_effect  mae_vs_truth  zero_credit_channels
     1        13           0.00000          0.32239                 0.00008       0.08333                    12
     2       152           0.11184          0.32248                 0.00001       0.08333                    12
     3      1300           0.36077          0.32249                 0.00000       0.08333                    12

  A first-order chain's state is the LAST TOUCH, so
  `display -> email -> convert` and `paid_search -> email -> convert`
  are indistinguishable once you are at `email`. That discards the path,
  which is the one thing a multi-touch model exists to use. Order 2 and
  3 can represent it, at the cost of state explosion: 13 states at order
  1, 1300 at order 3, with the share of states seen fewer than ten times
  going 0.000 -> 0.361.

BUT THE ORDER IS NOT THE INTERESTING RESULT HERE. EVERY CHANNEL GETS
EXACTLY ZERO CREDIT AT EVERY ORDER, and the largest removal effect
anywhere in the table is 0.000078.

  That is not a bug, and it is the most useful thing in this section.
  This implementation removes a channel by DELETING THE TOUCH FROM
  THE JOURNEYS and re-estimating -- the counterfactual a marketer
  means by 'what if we turned it off'. Done that way the conversion
  probability does not move, because in observational path data the
  outcome is attached to the JOURNEY, not to the path: a journey that
  converted still converted with one touch removed.

  The textbook removal effect avoids that by deleting the NODE FROM
  THE GRAPH and renormalising, which strands the removed node's
  inbound probability mass into the null state. That produces a
  satisfying non-zero number -- `markov_removal` in section F scores
  0.1082 MAE with it -- and the number comes from the graph
  representation rather than from anything about the channel.

  So the two implementations disagree completely, and the one that
  returns zeros is the one being honest. 'Remove the channel from
  the graph' was never a causal statement; this is what it looks
  like when you write down the counterfactual it claims to compute
  and then actually compute it.

  This project has been caught by the same brittleness before, in
  its milder form: markov once read 0.0000 for the planted channel
  AND for a channel with a true share of 0.089, and the accidental
  correctness of the first was reported as a detection.

  efficiency review. Its incremental CAC is infinite, because its
  incremental conversions are zero.

  That gap is the entire business case for the experiment, and it is
  now denominated in dollars rather than in credit shares.

F. THE UNOBSERVED CONFOUNDER -- WHY NO METHOD HERE CAN WIN
==============================================================================
The previous README ended with: 'the attribution simulator has no
unobserved confounders beyond the one I planted -- so every method here
performs better than it would on real data.' That is now false by
construction.

  `in_market` is a latent state affecting 32% of customers. It raises the
  probability of conversion by 0.160 AND multiplies exposure to CLOSING
  channels by 2.4x. It is never written to disk.

  The distinction from the planted retargeting confound matters. That
  one is observable in principle -- propensity is a customer attribute
  a good model could proxy. This one is not, and no attribution system
  in the world can condition on it: it is the thing the customer knows
  and the ad server does not.

         method  mae_vs_truth  credit_to_zero_effect_channel
         linear        0.0351                         0.0884
     time_decay        0.0354                         0.1235
        shapley        0.0360                         0.1397
shapley_sampled        0.0581                         0.1727
     last_touch        0.0590                         0.2027
    first_touch        0.0780                         0.0170
 markov_removal        0.0944                         0.3033

  EVERY method credits the zero-effect channel, and every method has
  non-trivial error against truth. Best MAE is 0.0351 by linear.

  The useful reading is not the ranking. It is that the ranking is now
  a comparison of how each method fails, rather than a search for the
  one that succeeds -- because with an unobserved common cause of
  exposure and outcome, none of them CAN succeed. That is a theorem,
  not a limitation of these implementations.

  Which is why the geo holdout in the main report is not a nice-to-have
  and not a validation step. It is the only instrument that answers the
  question at all, and its cost -- foregone spend in control markets --
  is zero in exactly the world where the channel is worthless.
